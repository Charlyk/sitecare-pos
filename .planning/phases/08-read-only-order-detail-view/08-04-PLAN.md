empty — and close the reachable mutating control that violates SC3 on the read-only route today.

card. SC3 requires that no mutating control is reachable — and the Modify button at line 131 is
reachable **in production right now** (see finding F-01 below), not merely at risk once hydration
lands.

Output: an items card that shows skeleton rows while fetching, an inline retryable message when the
fetch fails, an explicit line when the order genuinely has no items, and no reachable mutating control
under `readOnly`.
</objective>

<planner_finding id="F-01">
## ⚠ A load-bearing premise in RESEARCH.md and CONTEXT.md is false — verified

Both documents state that the `AdminOrder` summary reaches `screen-detail.jsx` with a **null** items
value, and that the screen therefore "degrades gracefully to the minimal totals card"
(`screen-detail.jsx:191-204`). RESEARCH Pitfall 4 builds on this, saying the Modify defect is
"invisible until this phase actually hydrates `items[]`".

**This is false.** It was verified by executing `normalizeOrder` against an `AdminOrder`-shaped object:

- `normalizeOrder` (`src/data.jsx:245`) maps `items: (o.items ?? []).map(...)` — it returns an **empty
  array**, never null.
- `use-history-orders.js:29` runs every summary through `.map(normalizeOrder)`.
- `store.js` `openHistoryOrder(order)` stores that normalized object.
- Therefore `historyOrder.items` is `[]`, and `order.items != null` — the gate on lines 37, 123, 191,
  and 208 — is **already true** on the history-detail route.

The claim survived because both test fixtures are hand-written and unrepresentative:
`app-history-route.test.jsx:52` sets `items: null` explicitly, and `screen-detail.test.jsx`'s
`HISTORY_ORDER` omits the key entirely (`undefined`). Neither shape is what production produces.

**Three consequences this plan must be built on:**

1. **The Modify button is reachable in production today.** SC3 is violated on the shipped
   `history-detail` route, not prospectively. Task 2 is a live defect fix, and its severity in the
   threat register reflects that.
2. **The minimal-totals-card fallback (lines 191-204) is unreachable** on both routes — `normalizeOrder`
   is applied to the live route's payload too. It is dead code. **Do not delete it in this phase**
   (no CONTEXT decision authorises that, and it is Phase 7 code shipped days ago) — but do not build the
   loading or error states on top of it either, because it will never render.
3. **The pre-hydration state is an *empty* receipt, not an *absent* one.** This is the single most
   important consequence: `items.length === 0` is true both while loading and when an order genuinely
   has no items. UI-SPEC E4 treats the empty case as a rare "data anomaly", but under the real shape it
   is also the state of **every open, on every order, before the fetch resolves**. Keying the empty
   message on the items value alone would flash "No items on this order" on every single open. The
   states must be distinguished by **query state** (`detailLoading` / `detailError`), which is why this
   plan's state machine is ordered the way it is and why the prohibition above exists.

UI-SPEC's "Items-Card Error State" says the error block replaces "the entire items-card content
(header + rows)". Under the real shape that would also destroy the totals block, which lives *inside*
the items card at lines 171-185 and renders `AdminOrder` subtotal/total that the app already holds —
directly violating SC2's "the `AdminOrder` fields already fetched stay visible rather than blanking".
UI-SPEC was written assuming a separate totals region above the card. **This plan therefore scopes the
skeleton and the error block to the rows region only, keeping the card header slot and the totals
block.** This is a deliberate, surfaced divergence from UI-SPEC's letter in service of its own stated
intent and of SC2. Flag it if that reading is wrong.
</planner_finding>
