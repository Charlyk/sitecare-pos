    ## Important: setAuthError integration

    The `error` prop on LoginScreen comes from `authError` (from `useAuth()`).
    `authError` is set by `signIn()` in `auth.jsx` when the API returns a 401.
    The existing `setAuthError` (which is `setError` from the auth context) can be used to clear the error when the user starts typing — but this clearing is handled inside `LoginScreen` already (each `onChange` calls `setError(null)` in the component's internal handler). No additional wiring needed here.

    The LoginScreen also performs its own client-side email validation (before calling onSubmit). When the email regex fails, LoginScreen sets its internal `error` state to `'email'`. This is component-internal — it does NOT go through `authError`. The parent's `authError` only represents server-returned credential errors.

    For this reason, LoginScreen needs to manage two sources of error:
    - Internal email validation error (`'email'`) — set within the component
    - External auth error passed via `error` prop (`'creds'`)

    The component already handles this via its internal `error` state initialized to `null` and set by the `handleSubmit` logic. The external `error` prop from auth.jsx overrides the internal error display when `authError` is `'creds'`. The simplest implementation: in LoginScreen's display logic, use `authError || internalError` — but since LoginScreen already has an internal error state, the cleanest approach is:
    - LoginScreen uses its own `[error, setError]` state for the email validation guard
    - When the `error` prop from the parent changes (authBusy goes false after a failed signIn), sync it to the local state:

    This synchronization should already work naturally if LoginScreen's display checks both its own `error` state and the prop. The executor should verify this during the human-verify checkpoint.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated renderer | Any code path that reaches Shell without isAuthenticated=true |
| opener plugin call | JS calls open() to send a URL to the OS browser — URL must be hardcoded, not user-supplied |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-11 | Elevation of Privilege | Auth guard bypass | mitigate | Guard checks Zustand `isAuthenticated` which is only set to `true` after `adminClient.auth.getSession()` succeeds — not just after a token is retrieved. Cold-start with a stale token deletes the token and stays on login. |
| T-02-12 | Tampering | open() URL injection | mitigate | The forgot-password URL is a hardcoded string constant `'https://restaurant.sitecare.ro/reset-password'` in app.jsx — not constructed from user input. |
| T-02-13 | Information Disclosure | LoginScreen renders over Shell briefly | mitigate | `authBusy` renders a white blank div during keychain check — LoginScreen and Shell are mutually exclusive render paths, no flash of protected content. |
</threat_model>
