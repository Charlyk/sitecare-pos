is unused."* Everything else in the phase is UI on top of this seam.
Output: a parameterized hook, and a test file whose premise matches it.
</objective>

## Assumption Delta — `chosen` (D-06 family: constant → parameter)

**Signal.** The `assumption-delta scan` detector fired two signals on this phase's scope:
`chosen` (on *"Staff can pick a **custom** start and end date"*) and `pluralization` (on *"no
**second** data source"`).

**The `chosen` delta — the real one.** `getLast30DaysRange()` was a *derived constant*: one frozen
range, computed inside the hook, with no caller input. Phase 9 makes the range a *chosen parameter*.
A configuration decision (which 30 days?) has become a modeling decision (what is a range, and who
owns it?).

**The noun that is now primary:** **the resolved range** (`{ from, to }`) — not "the last 30 days",
and not "the selected period". The range is what the query key is built from, what the cache is
partitioned by, and what the rendered period label must describe (D-06). The *period* (`'today'`,
`'7'`, `'30'`, `'custom'`) is now a detail of how one particular range came to be chosen, not the
thing the data layer knows about.

**Decision: `promote`.** The general representation (an arbitrary `{ from, to }`) becomes the hook's
primary and only contract; the 30-day case is demoted to one of several builders in
`history-utils.js` (09-01), with no special standing inside the hook. Explicitly rejected:
`add-alongside` — i.e. keeping the zero-argument `useHistoryOrders()` as a "default 30 days" overload
beside a new `useHistoryOrders({from, to})`. That would have been the lower-diff move (no test file
churn — see RESEARCH Pitfall 5), but it preserves exactly the frozen-at-mount trap this phase exists
to remove, and it leaves two ways to ask for the same data, one of which silently ignores D-06's
label-follows-data requirement because it has no range to report.

**Contrast with Phase 7's decision.** `07-02-PLAN.md` recorded an `add-alongside` for
`openHistoryOrder`/`history-detail`, and `08-05` confirmed it terminal for that phase. That was
correct there — two genuinely different routes with diverging data needs. This is the opposite shape:
one route, one data need, one range — where a second overload would be pure ambiguity. The two
decisions do not conflict.

**The `pluralization` signal — `no-change`.** *"no second data source"* is `P7 D-15`'s already-settled
decision (`getAdminDashboard` dropped permanently), restated in this phase's SC3 as the reason the
summary strip retargets for free. It is a record of a removal, not a new second-of-a-kind. Nothing to
promote. `09-COVERAGE.md` re-affirms the opt-out from a full-coverage baseline rather than carrying
it over silently.

**Suggested (not required) companion:** the cache-reuse test in Task 2 (apply range A → switch to B →
switch back to A, assert the SDK call count does not increase) is the contract test that encodes the
now-generalized intent: the range, not the period, is the identity of a fetch.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied range → SDK query | `from`/`to` now originate from user interaction (a pill click or a typed date) rather than from a constant computed in-process. This hook is the last code between that input and the network call. |
| History cache root → live-order cache root | `['history-orders', ...]` vs `['orders']`. `use-sse.js` writes live kitchen-shaped orders into `['orders']` via `setQueryData`; a key collision would let SSE corrupt the admin-shaped archive. |
| SDK error object → thrown Error message | `result.error.error` is a server-controlled string that becomes an `Error` message. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

Task 2's rewritten stable-key test pins the guarantee from the caller's side: a new object literal with identical strings must not refetch. 09-04 carries the matching `useMemo` requirement and its own test.
