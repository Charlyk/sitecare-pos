# Phase 10 — UI Design Contract

> Visual and interaction contract for Filters + Search. Generated by gsd-ui-researcher, verified
> by gsd-ui-checker. This phase inherits the already-shipped design system
> (`src/colors_and_type.css` + `src/styles.css`) and the already-shipped inert filter bar
> (`src/screen-history.jsx:294-345`, `P7 D-14`) — this contract does **not** invent a new visual
> language. It (1) activates the status pills that already exist in final visual position and
> adds live-count badges, (2) specs the ONE genuinely net-new control group this phase adds — the
> type filter, which the current bar never ported (F-03) — (3) restructures the bar into the
> design's two-row shape (D-07) so the type group fits, (4) specs the debounced search box's
> activation, (5) specs the filtered-empty-state's second copy variant and its clear-filters
> remedy (D-13, D-14), and (6) specs the Avg-tile's zero-vs-error-glyph gating fix (D-15) that
> this phase makes reachable for the first time. All decision IDs below (`D-01`…`D-15`, `F-02`,
> `F-03`) refer to `10-CONTEXT.md`.

**Scope note:** The period presets, the custom-range popover, and the period-switch
loading/error/copy behaviors ship from Phase 9 (`09-UI-SPEC.md`) and are reused verbatim — this
contract does not re-spec them. Reprint and CSV export stay inert (Phase 11); the Export button's
inert visual is untouched. The day-grouped list's row/table rendering, the first-load skeleton,
and the detail route shipped from Phase 7/8 and are reused verbatim — this contract covers what
filtering and search touch: the filtered *input* to `groupOrdersByDay`/`computeSummary` (D-04),
**and the one tile-output change this phase itself introduces** — the Avg tile's zero-vs-error
gating condition (D-15), which becomes reachable for the first time once a status filter can
reduce `completedCount` to zero while other rows remain visible. See the Summary Strip / Avg-Tile
Contract below — this is not covered by "reused verbatim."

## Visual Hierarchy

**Unchanged from `07-UI-SPEC.md`/`09-UI-SPEC.md` — this phase does not shift the screen's focal
point.** The primary focal point remains the summary strip's Revenue tile value (20px/900), now
simply recomputed over a filtered input (D-04) rather than the whole period. This phase's two
net-new visual elements — the type-filter pill group and the count badges on the status pills —
are deliberately scoped to stay **recessive**, matching the existing filter bar's low-emphasis
register relative to the data below it:

- The type group's selected state uses a **cream** fill (`#f7f1e1`) with sage text — visually
  quieter than the status group's solid sage fill and the period group's solid dark fill. Three
  distinct selected treatments coexist in one bar; this is the design's own choice (ported as
  drawn, `10-CONTEXT.md` Claude's Discretion), not a case of one control reading as more important
  than the others.
- Count badges are small (11px/700), inset into the pill itself, and never compete with the
  20px/900 tile figures for attention.

The filtered-empty-state's Clear Filters button (D-14) is the phase's only new *actionable* copy
element and is deliberately styled `.btn-secondary` (neutral), not `.btn-primary` (accent) — it is
a recovery action, not a primary conversion CTA, and this screen already reserves accent-fill
buttons for the Phase 9 popover's Apply action.

## Faceted Status-Count Contract (D-01, D-02, D-03)

**The count on each status pill always answers "what do I get if I click this?"** — computed
against type + search but **not** against the status selection itself (D-02's exclude-self
faceting). This means two derived lists exist side by side: one filtered by type+search only (for
counts), one additionally filtered by status (for rendered rows) — a single `.filter()` pass
cannot produce both (⚠ load-bearing per D-02, flagged for the planner, not resolved by this visual
contract).

**Visual treatment — ported verbatim from the design source
(`sitecare-orders/project/src/screen-history.jsx:241-247`):**

```
[ Toate 240 ] [ Finalizate 198 ] [ Rambursate 12 ] [ Anulate 30 ]
  ^^^^^^^^^^ selected: var(--sc-primary) fill, white text + white-tinted badge
             ^^^^^^^^^^^^^^^^^ unselected: transparent, #555 text + grey badge
```

- Badge: `fontSize: 11`, `fontWeight: 700`, `padding: '1px 6px'`, `borderRadius: 999`,
  `background: selected ? 'rgba(255,255,255,0.25)' : 'hsl(120 10% 90%)'`. Text color is
  `currentColor` (inherits the button's own selected/unselected text color) — never set
  independently.
- **D-03 (zero stays clickable):** a `0` count renders with the identical badge style — no
  dimming, no `disabled`, no separate "empty" treatment. Clicking it is a normal filter action
  that lands on the filtered-empty-state (below). This deliberately avoids overloading grey: this
  screen already uses opacity for *unready feature* (Export, still inert this phase) and, once
  Phase 9 ships, for *loading* — a third grey meaning would be unreadable.
- **Pill order corrected to match the design/requirements (F-03):** production's inert bar today
  orders `All / Completed / Canceled / Refunded`; this phase reorders to `All / Completed /
  Refunded / Canceled`, matching `sitecare-orders/project/src/screen-history.jsx:164-165` and
  `REQUIREMENTS.md`'s HIST-07 wording exactly. This is a correction, not a new design choice — the
  design has always been authoritative here (Claude's Discretion in `10-CONTEXT.md`, resolved).
- **`All`'s count** = the number of matches of type + search alone (D-02) — not the unfiltered
  period total, and not the sum of the other three pills' displayed counts (which would double
  count nothing here, per the `deriveDisplayStatus` precedence invariant already verified in
  `history-utils.js`, but would still be the wrong number to *read off* as `All`'s definition).

## Filter Bar Structure Contract (D-07)

**Ports the design's two-row shape exactly** — confirmed by
`sitecare-orders/project/screenshots/desktop-history.png` (1440×900, the app's exact default
window size), which shows search + export wrapping to their own right-aligned second row. This is
the design's intent, not a layout failure to design around.

```
Row 1 (flex-wrap, left-aligned):
[ Period pills ]  [ Status pills + counts ]  [ Type pills ]

Row 2 (marginLeft: auto container, right-aligned — wraps here once Row 1 fills):
                                          [ Search 220px ]  [ Export (inert) ]
```

- **Nesting change required:** production's current structure has Search as a standalone flex
  child and only Export in an auto-margin div — adding the type group to that shape strands search
  on row 1 and Export alone on row 2. This phase nests **both** search and Export inside ONE
  `marginLeft: 'auto'` container (matching `sitecare-orders/project/src/screen-history.jsx:260`),
  so they wrap together.
- **Fit:** row 1 measures ~990px against 1152px available (1440 window − 240 sidebar − 2×24
  `content-pad`), leaving headroom for Phase 9's widened custom-range pill. `flexWrap: 'wrap'`
  (already present at `screen-history.jsx:314`) degrades gracefully on a narrower window — no
  `minWidth` is set in `tauri.conf.json` and the window is resizable.
- **Rejected (per `10-CONTEXT.md`):** icon-only type pills to force one row (discards the existing
  `delivery`/`pickup`/`dinein` i18n labels and diverges from the design); a type dropdown (a new
  control pattern nothing else on this screen uses).

## Search Contract (D-09, D-10, D-11)

**Activation only — no new visual chrome.** Removes `disabled` from the existing `.search` input
(`screen-history.jsx:333-336`) and wires `onChange`. No new icon, no new class, no new size.

- **What it matches (D-09):** exactly what the row renders — `dailyOrderNumber` (or the `id[0:8]`
  fallback shown when `dailyNumber` is null) plus `customer.name`. No row is unreachable by the
  text printed on it. Matches the existing `h_search` label (`Caută după # sau client` /
  `Search by # or customer`) — no label change needed.
- **Debounce (D-10):** 250ms on typing; **clearing the box (or emptying it via backspace to `''`)
  applies immediately**, no debounce delay. There is **no loading/spinner affordance for the
  debounce window** — deliberately: 250ms sits below the ~300ms perceptible-lag threshold, and
  everything is client-side, so this governs render churn, not a network wait worth signaling.
- **Diacritic folding (D-11):** query and customer name are both NFD-normalized with combining
  marks stripped before comparison (a Romanian POS: `ș`/`ț` are habitually typed as `s`/`t`). This
  is a matching-logic detail with no visual surface of its own — no new UI state, no new copy —
  included here only so the ui-checker and executor see the full contract in one place.
- **No result-count indicator inline in the search box itself** — the existing summary strip and
  day-group counts (both recomputed per D-04) are the feedback surface; the search input stays
  visually identical to `screen-orders.jsx`'s precedent (undebounced there, debounced here — timing
  only, not appearance).

## Summary Strip / Avg-Tile Contract (D-04, D-05, D-15)

**The four tiles recompute from the FILTERED set, not the period (D-04)** — `computeSummary`
already accepts any list, so this is a change of input only, reusing `SummaryStrip` verbatim.
This is the one place in this phase where a filter's effect is not "which rows render" but
"what number a tile shows" — and D-15 is a **gating-condition fix**, not just a number change,
so it is specified here explicitly rather than left implicit in "tiles follow the data."

**D-15 — the blocking fix.** Filtering to `Completed only` was always safe (the whole visible set
is completed, `avg` is a real number). Filtering to **`Canceled only`** or **`Refunded only`**
makes `completedCount === 0` while rows are still visible on screen — a state Phase 7 never had
to handle, because before this phase the only way to reach `completedCount === 0` was an empty
period (`isEmptyState === true`). Phase 10 makes a **second** route to `completedCount === 0`
reachable: a non-empty, successfully-filtered screen with zero *completed* orders in view.

- **The existing gate is wrong for this new route.** Today (`screen-history.jsx:251`):
  `summary.avg === null ? (isEmptyState ? formatRON(0) : '—') : formatRON(summary.avg)`. Under a
  Canceled-only filter, `avg === null` (true) but `isEmptyState` is `false` (canceled rows are on
  screen) — the tile would render `'—'`, the em-dash **error** glyph, during a completely
  successful filter. That is the exact bug this decision exists to prevent.
- **The fix, stated as a visual directive:** the gating condition must change from
  **`isEmptyState`** to **"not an error"** (`isError` being the only thing that should ever
  produce the em-dash). Concretely: `summary.avg === null ? (isError ? '—' : formatRON(0)) :
  formatRON(summary.avg)`. The Avg tile renders a computed **`0`** (via `formatRON(0)`, exactly
  like every other RON figure on this screen — no special "zero" styling, no dimming, no asterisk)
  in **every** `completedCount === 0` case that is not a true fetch error: an empty period (the
  original Phase 7 case, unchanged in outcome) **and** a non-empty filtered view with zero
  completed orders (this phase's new case).
- **The em-dash (`'—'`) keeps exactly one meaning on this screen: a true fetch error
  (`isError === true`).** This carries forward `07-UI-SPEC.md`'s and `09-UI-SPEC.md`'s "one error
  treatment" rule and extends it from error *states* to the error *glyph* itself — the glyph must
  never appear as a side effect of a successful filter, only as a side effect of `isError`.
- **D-05 (accepted, unaffected by this fix):** under `status = Completed`, the Refunds tile still
  reads `0 · 0 canceled` and can only ever read zero — this is a separate, already-accepted
  consequence of D-04's "one rule, no carve-outs," not something this gating fix changes. The
  Refunds tile has no null-average ambiguity to begin with (it is a plain count, never `null`), so
  D-15's fix does not touch it.
- **No new visual chrome.** No new color, no new size, no new icon — this is a gating-logic
  correction to which of two already-existing renders (`formatRON(0)` vs `'—'`) a tile falls into,
  not a new tile design.
