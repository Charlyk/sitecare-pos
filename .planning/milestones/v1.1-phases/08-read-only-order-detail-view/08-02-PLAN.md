Add the two pure derivation pieces the read-only detail view needs, in the module layer where they can
be unit-tested without a DOM: a `deriveDuration(order)` helper, and an export of the existing
`historyStatusMeta` mapping.

"Completed" in one place and "Refunded" in the other. Both are pure functions. Putting them here — not
inline in `screen-detail.jsx` — means the tricky cases (no terminal event, two COMPLETED events, equal
timestamps) get direct unit tests instead of being probed through rendered DOM.

Output: `deriveDuration` exported from `history-utils.js` with full edge coverage, and
`historyStatusMeta` exported from `screen-history.jsx` with its behavior unchanged.
</objective>

<edge_assumptions>
The deterministic edge probe returned three `unresolved` edges for HIST-10. Two are resolved here
against this phase's real behavior and are encoded as `must_haves.truths` above. They are planner
assumptions, surfaced rather than silently decided — flag them if the intent differs:

- **`empty` — "What is the result for empty, single-element, or null input?"** Assumed: an order with
  `events: []`, `events: undefined`, or events carrying no terminal status yields **no duration row at
  all** — not "0 min", not "—". This follows the Claude's-discretion note in `08-CONTEXT.md` ("do not
  render a partial or misleading number") and UI-SPEC E1's `empty`/`partial` rows. A single-element
  `events[]` holding the terminal event is a normal populated case, not an edge.
- **`adjacency` — "When two things are exactly equal or just touch, do they merge, collide, or
  separate?"** Assumed: two COMPLETED events with an **identical** `createdAt` do not collide — the
  later array element wins, deterministically. UI-SPEC E1 specifies "last matching event wins" by
  `createdAt`, which leaves an exact tie undefined; array order is the only remaining signal, and
  "last wins" is the consistent reading. The load-bearing property is determinism, not which of two
  identical timestamps is picked: the same payload must always render the same duration.

The third (`ordering`) concerns item-row rendering order and is resolved in 08-04.
</edge_assumptions>

  <action>
Export a new pure function `deriveDuration(order)` from `src/history-utils.js`, placed after
`deriveDisplayStatus` (it is the same family of derivation and shares its raw-SDK-casing convention).

Signature and contract:
- Returns `{ kind: 'prep' | 'canceled', minutes: number }`, or `null`.
- `null` whenever a trustworthy number cannot be produced: no `order.placedAt`, no `order.events`, an
  empty `events[]`, or an `events[]` carrying neither terminal status.
- Selects the terminal event by filtering `order.events` on `e.toStatus === 'COMPLETED'` (then, only if
  none matched, `'CANCELLED'`) and taking the event with the **maximum** `createdAt`. Use a reduce with
  a `>=` comparison so the later array element wins an exact timestamp tie — deterministic per the
  `adjacency` edge above. Do not use `Array.prototype.find`: it returns the first array match, which
  RESEARCH Pitfall 5 identifies as producing a stale duration on a re-completed or corrected order.
- `COMPLETED` is checked before `CANCELLED` and wins outright when both exist, regardless of which is
  later — an order that completed and later received a correction event still reads as completed.
- `minutes` = the difference between the winning event's `createdAt` and `order.placedAt`, in minutes,
  clamped at a floor of 0 via `Math.max(0, ...)`.
- Skip events whose `createdAt` does not parse (`Number.isNaN` on the parsed time), rather than letting
  a NaN propagate into the returned minutes.

Use `Math.round` for the minute conversion, not `Math.floor`. This diverges deliberately from
`elapsedMinutes` in `data.jsx`, which floors because it is a live ticking counter where rounding up
would show a minute that has not elapsed yet. `deriveDuration` is a fixed historical measurement where
rounding to the nearest minute is the more accurate report. Note the divergence in the JSDoc so the
next reader does not "fix" it into consistency.

Two hard constraints from this module's header contract, both load-bearing:
- **Read `e.toStatus` with raw SDK casing** (`'COMPLETED'`, `'CANCELLED'`). `normalizeOrder` spreads
  `...o` and never rewrites `events[]`, so the lowercased values on `order.state` (`'done'`,
  `'cancelled'`) do not exist inside `events[]`. Using `order.state`'s vocabulary here silently matches
  nothing and returns `null` for every order.
- **Import nothing.** No `react`, no `data.jsx`, no `@charlyk/admin-client`. In particular do not reach
  for `formatDuration` — returning raw minutes and letting the caller format is what keeps this module
  DOM-free and testable.

Write the JSDoc in the same style as the existing exports, citing D-10 and UI-SPEC E1 for the
last-matching-event rule.
