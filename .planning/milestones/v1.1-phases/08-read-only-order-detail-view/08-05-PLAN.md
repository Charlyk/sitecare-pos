<assumption_delta_decision>
**Signal:** the assumption-delta scan returns `detected: true` for this phase. Its literal signal (the
word "fallback" in SC2) is a prose false positive, but a real generalization does sit underneath it, and
Phase 7 named it in advance. `STATE.md` records: *"Routing decision: `add-alongside` (`openHistoryOrder`
/ `screen: 'history-detail'`) rather than generalizing `openOrder()`. Recorded as accepted debt in
`07-02-PLAN.md`'s `<assumption_delta_decision>`; **the next phase's `getOrder(id)` is what should force
a promote**."* This is that phase.

**The noun that is now primary:** *the order detail route*. It was singular — one route, one
`selectedOrder`, one `useOrderDetail` call. This plan makes it plural: two routes, two store slots, two
`useOrderDetail` calls against the same `['order', id]` cache key, one presenter serving both.

**Decision: `add-alongside`.** Not `promote`, despite the standing preference for promotion when a
generalization occurs, and despite Phase 7 predicting this phase would force one.

**Rationale:** `08-CONTEXT.md` D-04 is a locked user decision and it specifies add-alongside explicitly
— *"Add a sibling `useOrderDetail(historyOrder?.id)` call next to the existing live-route call."* The
user reached this twice over (D-01 and D-04), both times choosing the option that writes the least new
code, and `08-CONTEXT.md`'s `<specifics>` records the reasoning as deliberate ("Reuse over purity,
twice"). A locked decision is not the planner's to reverse on architectural preference. Promoting would
also mean unifying `openOrder`/`openHistoryOrder` and collapsing two routes into one flag-driven route
— a refactor with no user-visible benefit, touching the shipped live order path that Phase 7 was careful
to keep byte-identical.

**Accepted debt:** two call sites of the same hook against the same cache key, two store slots with
near-identical lifecycles, and one presenter with a `readOnly` flag plus three optional props whose
meaning depends on which caller supplied them. The cost is that a change to detail-fetching behavior now
has to be made twice, and it is possible for the two routes to drift.

**What would force a promote:** (a) a **third** caller of `OrderDetailScreen` — Phase 11's reprint is
the near-term candidate; three parallel copies is where add-alongside stops being cheaper than
generalizing; (b) the two routes' data needs **diverging** in a way that requires editing
`useOrderDetail` — the deferred "status-specific error copy" idea is exactly this, since it would need
the hook to preserve the HTTP status that D-01 locks it into discarding; or (c) the props on
`OrderDetailScreen` growing past this phase's `readOnly` + three, at which point the presenter is
serving two components' worth of contract.

**Suggested (not required) invariant:** a test asserting both routes render `OrderDetailScreen` from the
same `['order', id]` cache entry — encoding D-02's "one order, one truth" so a future snapshot or
divergent-key change trips it deliberately rather than silently.
</assumption_delta_decision>

Add a second `useOrderDetail` call to `App()` in `src/app.jsx`, immediately after the existing
live-route call at line 70:

  `const { data: historyDetail, isPending: historyDetailPending, isError: historyDetailError, refetch: refetchHistoryDetail } = useOrderDetail(historyOrder?.id);`

**Placement is a correctness requirement, not a style preference.** It must sit in the same
unconditional block as the line-70 call — above the `coldStartBusy` return at line 207 and the
`!isAuthenticated` return at line 212. React requires every hook to be called unconditionally in the
same order on every render; a hook added below an early return runs on only some renders and throws
"Rendered fewer hooks than expected" the moment those guards flip, which is exactly at sign-in and
sign-out. `STATE.md` lists this under Critical Watch-Outs, and `useSSE`/`useOrders`/`useUpdater` are all
already placed this way for the same reason.

No guard is needed for a null `historyOrder`: `historyOrder?.id` yields `undefined`, and the hook's
`enabled: !!client && !!id` disables the query. That is why D-01's unchanged hook works here verbatim.

Then build the merged object, near the same block:

  `const mergedHistoryOrder = historyOrder ? { ...historyOrder, ...(historyDetail ?? {}) } : null;`

Hydrated fields win (D-03). This is only safe because **both sides have already been through
`normalizeOrder`** — `use-history-orders.js` maps the summary through it, and `useOrderDetail` returns
`normalizeOrder(result.data.order)` — so the field names align (`state`, `type`, `total`, `customer`,
`placedAt`) and money is already in RON on both sides. Do not re-divide anything by 100 here. Guard the
spread with `?? {}` so a pending or errored query merges nothing rather than spreading `undefined`.

Do **not** reach for TanStack's `placeholderData` or `initialData` instead. The query resets to
`undefined` on error, which would blank the screen — the opposite of what D-07 and SC2 require. The
manual spread is the correct pattern here, not a lesser one.

**Use `isPending`, not `isFetching`, for `detailLoading`.** This resolves RESEARCH Open Question 1 and

"we have nothing to show yet", which is what the skeleton is for.
