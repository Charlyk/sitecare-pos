# Debug Session: windows-history-network-error

## Symptoms (from user)

- **Expected:** Order history loads on the History screen (Windows build).
- **Actual:** History fetch fails with a network error; the app reports "no internet connection."
- **Error message:** "no internet connection" (user paraphrase — likely a Chromium/WebView2 `ERR_INTERNET_DISCONNECTED` / "Failed to fetch" surfaced to the user).
- **Platform:** Windows-only. macOS works fine.
- **Timeline:** Never worked on Windows (not a regression).
- **Reproduction:** Open History screen on the Windows desktop app while connected to the internet.
- **Contrast (works on same machine):** App receives live orders via SSE; Menu screen loads. So the network path to the API is generally functional on this Windows machine.

## Current Focus

- hypothesis (re-ranked after (A)/(B), see Evidence for full reasoning):
  1. **TOP — malformed/large-response HTTP framing on `/v1/admin/orders` only.** The server (Railway edge, `server: railway-hikari`) mis-sizes or mis-chunks the response specifically for this endpoint's larger, dynamic payload (Content-Length/Transfer-Encoding mismatch, premature close, or a proxy timeout under load/latency), and WebView2's Chromium/Blink net stack aborts strictly (`net::ERR_CONTENT_LENGTH_MISMATCH` / `ERR_INCOMPLETE_CHUNKED_ENCODING` / `ERR_CONNECTION_CLOSED` / a 5xx from the edge), while macOS's WKWebView (WebKit/Safari engine — NOT Chromium, correcting the prior framing) tolerates the same malformed response or the restaurant's macOS testing simply never exercised a large enough payload. This is now DIRECTLY testable via the shipped diagnostic (see Resolution/Evidence below) without needing DevTools.
  2. **SECOND — plain response size/duration** (large 30-day default payload on a slower/higher-latency Windows-side connection) tripping a stall/idle timeout. Slightly below #1 because SSE (a long-lived connection) working fine on the same machine argues against generic slowness, though SSE and a single large batched fetch fail very differently, so this isn't a strong disconfirmation.
  3. **THIRD, downgraded near the bottom** — percent-encoded colons (`%3A`) in the `from`/`to` query string. Downgraded because encoded colons in query strings are ubiquitous across the web (any ISO-8601 filter) with no known WebView2/Chromium rejection class; low prior from first principles. Not worth further dedicated testing.
  4. Windows-side `/admin`-path interception (antivirus/proxy/DLP) — ELIMINATED this cycle (see Eliminated): the other two `/v1/admin/*` calls on this same machine succeed, so the fault is isolated to this one request, not the path prefix or the namespace.
- **Critical reframing (code-read finding, this cycle):** the user's "no internet connection" paraphrase is NOT literal browser/OS text — it is `ErrorBlock`'s own generic two-line copy (`h_error_title` = "Couldn't load history" + `check_connection` = "Check connection and try again.") rendered for **any** `isError` state, whether caused by a true network-layer failure, an HTTP error status, or a client-side exception. Until this cycle we had **zero evidence** the failure is actually network-layer at all — that was an unverified assumption baked into the hypothesis set from session start. This is now fixed: `use-history-orders.js`'s queryFn discards this distinction; the diagnostic build (this cycle) restores it.
- test: Two tests now available, one FREE (no build needed), one requires shipping the diagnostic build:
  1. **FREE, do this first:** On the affected Windows machine, right now, on the current production build, open History and click the "Today" (Azi) period pill, then "7 zile". Both request the same admin.orders.list endpoint with the same percent-encoded-colon query shape as the failing default "30 zile", but with a far smaller/faster response. If Today and/or 7-day succeed while 30-day fails, that both eliminates hypothesis #3 (colons) outright and strongly confirms #1/#2 (size/duration/framing). If ALL THREE fail identically, that argues against pure size/duration and raises weight on something structural to the endpoint itself (auth scope, a server-side bug independent of range).
  2. **Requires the diagnostic build** (implemented this cycle, not yet shipped): ship `use-history-orders.js` + `screen-history.jsx` + `i18n.jsx` changes via the auto-updater; on the Windows machine's next History failure, the ErrorBlock now shows a monospace technical-details line reading `{kind} {status?} · {message} ({errorName?}) · {ms}ms`, plus (when the failing range wasn't already "today") an automatic small-range probe result line. `kind: 'network'` means the SDK's `result.response` was `undefined` (fetch() itself rejected — genuinely never reached the server); `kind: 'http'` means `result.response` was a real Response with a `.status` (request reached the server, got a non-2xx) — this distinguishes "real network problem" from "server/application problem" for the first time this session.
- expecting: Free test result narrows to size/duration vs "fails uniformly regardless of range." Diagnostic build's `kind`/`status`/`ms` fields, if `kind: 'http'` with a status code (e.g. 500/502/504/413), points straight at a server-side bug independent of any WebView2 theory; if `kind: 'network'` with `errorName: 'TypeError'` and a short `ms`, points at an immediate connection-level rejection (CSP-like, DNS, or an aborted connection); if `kind: 'network'` with a long `ms` before failing, points at a stall/timeout consistent with #1/#2.

- timestamp: 2026-07-20 — Read `@charlyk/admin-client`'s `request()` implementation (`node_modules/@charlyk/admin-client/dist/index.mjs:655-777`). `throwOnError` is never set anywhere in this project (`auth.jsx`'s three `createAdminClient()` calls, `createConfig`'s defaults) — confirmed always falsy — so the SDK never throws synchronously; it always resolves. Two distinct failure shapes: (a) `fetch()` itself rejects (genuine network-level failure — DNS, connection reset, a WebView2 `net::ERR_*` abort) → SDK catches it and returns `{ error: caughtError, response: undefined }`; (b) `fetch()` resolves but `response.ok` is false (any non-2xx HTTP status) → SDK returns `{ error: parsedBody, response: <real Response with .status>, ...}`. The presence/absence of `result.response` is therefore an exact, reliable discriminator between "never reached the server" and "reached the server, got an error status" — a distinction the current `use-history-orders.js` (`throw new Error(result.error.error ?? 'Failed to load history')`) discards entirely.

## Eliminated

- hypothesis: Host-level CSP `connect-src` misses the API domain → ELIMINATED: domain is present and covers all paths; kitchen calls to the same host succeed.
- hypothesis: Admin calls use a different base host/subdomain → ELIMINATED: single `baseUrl` for all namespaces.
- hypothesis: Dev Vite proxy divergence → ELIMINATED: proxy is dev-only; production build calls the host directly.
- hypothesis: General loss of internet on the Windows machine → ELIMINATED: SSE + kitchen menu/orders work on the same machine simultaneously.
- hypothesis: Server-side redirect on `/v1/admin/orders` that Chromium/WebView2 re-checks against CSP `connect-src` (WKWebView more permissive) → ELIMINATED: direct `curl` shows no redirect on ANY path (admin, kitchen orders, kitchen menu) — all return a flat 401, no `Location` header, no 3xx.
- hypothesis: Admin endpoint has different CORS/preflight handling that only WebView2's stricter preflight enforcement rejects → ELIMINATED: `OPTIONS` preflight with the actual Windows Tauri origin (`http://tauri.localhost`) returns an identical 204 + echoed `Access-Control-Allow-Origin` for admin and kitchen paths alike.
- hypothesis: Query-param serialization (`from`/`to` ISO strings with `:`/`.`) produces a URL WebView2 mishandles or a WAF/proxy rejects → ELIMINATED: reconstructed the exact SDK-serialized URL, confirmed well-formed (`new URL()` parses cleanly) and reaches the live server normally (401 with fake token, not a network-level rejection).
- hypothesis: Windows build uses a different/stricter CSP via a platform-specific Tauri config override → ELIMINATED: only one `tauri.conf.json` exists; no `tauri.windows.conf.json`; CSP is byte-identical across platforms.
- hypothesis: `@tauri-apps/plugin-http` scope allowlist blocks the admin path → ELIMINATED: plugin not installed/used; SDK calls `globalThis.fetch` directly; no `http:*` capability permission granted in either capabilities file.
- hypothesis: Windows-side interception (antivirus/proxy/DLP/SSL-inspection) blocks or resets requests based on the `/admin` path prefix or the admin namespace generally → ELIMINATED: user confirmed the other two `/v1/admin/*` calls (`dashboard.getToday`, `settings.list`) succeed on the exact same Windows machine at the exact same time the app is failing on `/v1/admin/orders`. Any path-prefix- or namespace-level interception would have to also block those two calls; it doesn't. The fault is isolated to this one specific request.
